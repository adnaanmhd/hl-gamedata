## #1 [MAJOR] Second refix pass erases tree_sealed_at, re-opening already-paid footage for a second payment

**Where:** `tools/recal_refix_reset.py:314` · lane `regressions-r8` · refuter votes to refute: 0/2 (survives)

**Claim (finder, verified by both refuters):** The teardown UPDATE (lines 309-314) writes `tree_sealed_at=?` with `(now if paid_nodes else None, ...)`, where paid_nodes is recomputed from the CURRENT tree's DELIVERED nodes' accepted_reported_at (lines 181-187). But a sealed tree's re-delivered nodes can NEVER carry accepted marks — build_sheet_rows line 570 (`if sealed or n["accepted_reported_at"]: continue`) blocks their stamping precisely because of the seal. So on any second pass over a previously-sealed tree, paid_nodes is empty by construction and the existing seal is overwritten with NULL. The mixed-tree refusal (lines 181-198) reads only accepted_reported_at, never the existing tree_sealed_at, so it classifies the sealed tree's unpaid re-delivered node as plain 'unpaid delivered' and proceeds. Probe against the REAL tool + REAL build_sheet_rows (scratchpad probe_seal_erase.py): pass 1 on {paid p1, fix-failed p2} prints tree_sealed_at='2026-08-18T15:15:40+00:00'; sheet while sealed = []; pass 2 on the re-run tree (p1' delivered/unpaid, p2' fix-failed again) prints skipped_mixed: [], sealed_roots: [], and after pass 2 tree_sealed_at=None; the next sheet then counts ('paid@x.com', 0.47) and accepted_out stamps the re-delivered child — 1700s of footage already paid on the original sheet is paid a second time.

**Scenario:** Post-flip (after step 7.3 resumes dailies and accepted marks exist): a split tree has a paid DELIVERED child and a fix-failed REJECTED child. An operator runs recal_refix_reset --allow-reported to recover the fix-failed population — the tree seals and re-runs. The hard child fails its fixes again (the norm for genuinely difficult footage — that is why it was fix-failed). A later refix run automatically re-selects the tree (selection sweeps ALL fix-failed REJECTED rows; the operator does not pick roots), sails past the mixed check, erases the seal, and the following re-run's delivered hours land on the next payment sheet — the same footage paid twice, with sealed_roots: [] so the tool's own output reports nothing to reconcile. Ruling 7 explicitly names 'hours counted twice' under the new mechanism as a valuable finding; ruling 15 invites defects in the tree_sealed_at mechanism.

**Finder's proposed fix** (see plan §9 for the spec of record): In the teardown UPDATE, preserve an existing seal: seal_val = row['tree_sealed_at'] or (now if paid_nodes else None). Additionally, teach the mixed-tree refusal that an existing tree_sealed_at IS payment evidence: a sealed tree that now holds unpaid DELIVERED nodes is exactly the 'sealing swallows / unsealing double-pays' dilemma and should land in skipped_mixed for human reconciliation.
